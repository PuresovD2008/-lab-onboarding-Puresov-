3. Архитектурное решение методом WSM (Weighted Sum Model)

3.1. Обоснование весов критериев (сумма = 1.0)
- Гибкость изменения правил (вес 0.35): В системе бронирования ресурсов бизнес-правила (лимиты выдачи оборудования, правила бронирования, роли) меняются чаще всего. Возможность обновлять их без пересборки шлюза и миграций БД критически важна.
- Надежность (вес 0.30): После инцидента «Черная пятница» защита целостности данных и предотвращение записи некорректных значений имеют наивысший приоритет наравне с гибкостью.
- Производительность (вес 0.20): Важна для быстрого отклика API под нагрузкой, но уступает надежности и гибкости, так как проверка в памяти микросервиса занимает доли миллисекунды.
- TCO — стоимость поддержки и обучения (вес 0.15): Учитывается при выборе стека, но команда уже владеет языком разработки основного микросервиса.

3.3. Обоснованный вывод
Победителем по методу взвешенной суммы является альтернатива №2 — Application Layer (8.20 балла). Размещение основной логики валидации внутри микросервиса бронирования обеспечивает максимальную гибкость изменения сложных бизнес-правил (сравнение дат, проверка ролей, санитизация) и минимальный TCO за счет единого языка разработки.
Однако, учитывая критерий надежности (защита от прямых SQL-запросов и багов в коде), оптимальным архитектурным решением для проекта является гибридный подход:
- Application Layer выступает основным слоем валидации бизнес-логики, прав доступа и санитизации.
- Database Constraints (NOT NULL, CHECK end_date > start_date, CHECK count > 0) используются как второй рубеж обороны (Defense in Depth) для гарантированной защиты целостности данных на уровне СУБД.

4. Актуализация процессов Scrum (дополнения в Definition of Done)

1. Автоматизированное тестирование негативных сценариев API: Для каждого нового или измененного эндпоинта написаны интеграционные автотесты (отправляющие запросы напрямую в API в обход UI с невалидными типами, отрицательными значениями, XSS-нагрузкой и попыткой подмены ролей), и все тесты успешно проходят в CI-пайплайне перед мержем.
2. Обязательное ревью безопасности и валидации: Код проверен как минимум одним разработчиком по утвержденному чек-листу ревьюирования API, подтверждающему наличие серверной валидации входных DTO, проверки прав доступа и санитизации строковых полей, а статический анализатор безопасности (SAST) не выявил уязвимостей.
